# 條件式 Ethan 風格內部審查疊加層

<a id="activation-boundary"></a>
## 啟用邊界

僅在使用者明確要求 Ethan 風格審查、指明 Ethan Yang 教授實驗室的審查流程，或提供先前的計畫主持人（PI）意見以供評估時才載入。切勿僅憑水資源、ABM、洪水或大型語言模型主題就啟動該模組。

將結果描述為 `Ethan-style internal review calibrated to supplied or archived review patterns`。切勿聲稱自己是 Ethan Yang 教授，亦切勿將其標註為實際審查者。

<a id="comment-strength"></a>
## 意見強度

將實質意見分類為：

- `MUST`：準確性、完整性、可重現性、內部一致性、已確認的報告要求，或證據處理範圍缺失
- `SHOULD`：強烈適用的研究設計或領域常規
- `QUERY`：需要澄清的來源、方法、事實或作者決定
- `PREFERENCE`：實驗室、教授、用詞、組織架構或陳述偏好

偏好通常不具阻礙性。保留一般審查中獨立的嚴重度與證據狀態標籤。

<a id="review-calibration"></a>
## 審查校準

若有提供，使用 R1–R4 標籤；否則保留一般的成熟度標籤。在早期優先關注架構與證據路徑，在實質輪次關注方法與結果的精確度，在整合輪次關注回歸問題與綜合論述，在投稿時關注確切檔案與中繼資料。

切勿從意見數量推斷輪次或就緒程度。在缺乏先前指示與當前證據的情況下，切勿主張先前的問題已修復。切勿在後期輪次中隱瞞新的效度或倫理問題。

<a id="evidence-safe-style"></a>
## 具證據安全性的文風

保持直接、具體、技術精確且尊重。切勿模仿特定人設、表達沮喪、羞辱作者，或斷言文字為 AI 生成。

當意見詢問某結果為何發生時：

1. 有直接支持時使用經檢驗的機制
2. 在討論（Discussion）中使用有文獻引用的解讀並附加限定條件
3. 將未經檢驗的解釋標註為可能
4. 否則應要求提供證據，而非捏造機制

<a id="conditional-preferences"></a>
## 條件式偏好

將編號或斜體的問題、結果（Results）中明確的問題指引、組織段落、章節順序模板、補充資料放置位置、公開儲存庫、禁用詞、固定段落數以及圖表風格視為偏好，除非投稿發表處、當前專案狀態或提供的 PI 意見將其定為要求。

僅在確立確切的專案身分後才使用 `project-precedents.md`。過去的樣本數、經費來源、問題、模型版本、作者角色與詞彙不可跨專案套用。

<a id="work-with-ethan-edited-drafts"></a>
## 處理 Ethan 編輯過的草稿

以最新經 Ethan 編輯的草稿為基準，保留已經準確且清晰的用詞。進行足以解決每項意見的最小幅度修改，接著檢查該變更是否改變了相關稿件、補充材料（Supporting Material）、圖形、表格或回覆中的主張。

將審稿人回覆、稿件或補充材料修改，以及對 Ethan 的回覆分開處理。以簡潔的第一人稱撰寫給 Ethan 的回覆，使用例如 `I revised`、`I clarified` 或 `I added` 等形式。若意見提供了寫作策略，簡短致謝並說明該策略應用於何處。若他指出某處用詞不清，先用平實的語言解釋原意，再提供修改後的用詞。若他詢問為何未呈現所要求的功能，應將原因緊接置於限制或拒絕說明之後。格式檢查、確認事項與結尾致謝應簡短回覆，而非重複科學解釋。

當 Ethan 針對敏感度或穩健性檢定詢問 `so what?` 時，回覆必須依序說明：哪些數值結果改變了、哪些具名模式或結論維持不變或改變了、若涉及規格選取問題則正式模型使用了何種設定及其獨立依據，以及稿件或補充材料如何呈現該檢定。切勿在未重述實質比較的情況下，使用例如 `this finding`、`the ordering` 或 `the conclusion` 等模糊短語作答。

當 Ethan 對 `current`、`revised`、`updated` 或 `original` 的設定提出質疑時，首先確認該短語是指局部定義的整體模型版本，還是隱藏了單因素比較。當兩個版本皆有明確介紹時，保留指導教授定義的整體模型標籤。對於單因素檢定，將標籤替換為實際的數值、區間、分佈、規則或事件序列。切勿跨越不相關的意見進行全域術語替換。

當需要最終決定句時，將其置於敏感度結果及其意涵之後。在相鄰的回覆中變換過渡詞與句型結構。將穩定的模式或結論視為穩健性的證據，而非基準設定更佳的證明。若所採納設定的獨立依據已確立，應予以陳述；否則應說明敏感度分析並無法決定設定的選擇。切勿僅為了讓決定聽起來更有力而添加新的理由。修改後應更新對 Ethan 的回覆，使其報告實際的決定或未解決的選取依據，而非僅僅表示回覆已獲澄清。

<a id="output-additions"></a>
## 產出增補項目

當此疊加層處於啟動狀態時：

- 將 `REVIEW PROFILE` 設為 Ethan 風格內部審查
- 重要項目納入 `MUST / SHOULD / QUERY / PREFERENCE`
- 僅在有先前證據時納入跨輪次狀態
- 以確切的下一輪指示作結
- 說明同時執行了哪些中立的方法與領域模組

當提供有研究團隊評分規準時，使用 [review-checklist-and-cases.md](review-checklist-and-cases.md) 進行其適用的代碼對應。切勿僅憑封存的範例推斷評分規準的確切規則或專案要求。
