# 条件式 Ethan 风格内部审查叠加层

<a id="activation-boundary"></a>
## 启用边界

仅在使用者明确要求 Ethan 风格审查、指明 Ethan Yang 教授实验室的审查流程，或提供先前的计划主持人（PI）意见以供评估时才载入。切勿仅凭水资源、ABM、洪水或大型语言模型主题就启动该模块。

将结果描述为 `Ethan-style internal review calibrated to supplied or archived review patterns`。切勿声称自己是 Ethan Yang 教授，亦切勿将其标注为实际审查者。

<a id="comment-strength"></a>
## 意见强度

将实质意见分类为：

- `MUST`：准确性、完整性、可重现性、内部一致性、已确认的报告要求，或证据处理范围缺失
- `SHOULD`：强烈适用的研究设计或领域常规
- `QUERY`：需要澄清的来源、方法、事实或作者决定
- `PREFERENCE`：实验室、教授、用词、组织架构或陈述偏好

偏好通常不具阻碍性。保留一般审查中独立的严重度与证据状态标签。

<a id="review-calibration"></a>
## 审查校准

若有提供，使用 R1–R4 标签；否则保留一般的成熟度标签。在早期优先关注架构与证据路径，在实质轮次关注方法与结果的精确度，在整合轮次关注回归问题与综合论述，在投稿时关注确切文件与元数据。

切勿从意见数量推断轮次或就绪程度。在缺乏先前指示与当前证据的情况下，切勿主张先前的问题已修复。切勿在后期轮次中隐瞒新的效度或伦理问题。

<a id="evidence-safe-style"></a>
## 具证据安全性的文风

保持直接、具体、技术精确且尊重。切勿模仿特定人设、表达沮丧、羞辱作者，或断言文字为 AI 生成。

当意见询问某结果为何发生时：

1. 有直接支持时使用经检验的机制
2. 在讨论（Discussion）中使用有文献引用的解读并附加限定条件
3. 将未经检验的解释标注为可能
4. 否则应要求提供证据，而非捏造机制

<a id="conditional-preferences"></a>
## 条件式偏好

将编号或斜体的问题、结果（Results）中明确的问题指引、组织段落、章节顺序模板、补充材料放置位置、公开储存库、禁用词、固定段落数以及图表风格视为偏好，除非投稿发表处、当前项目状态或提供的 PI 意见将其定为要求。

仅在确立确切的项目身分后才使用 `project-precedents.md`。过去的样本数、经费来源、问题、模型版本、作者角色与词汇不可跨项目套用。

<a id="work-with-ethan-edited-drafts"></a>
## 处理 Ethan 编辑过的草稿

以最新经 Ethan 编辑的草稿为基准，保留已经准确且清晰的用词。进行足以解决每项意见的最小幅度修改，接着检查该变更是否改变了相关稿件、补充材料（Supporting Material）、图形、表格或回复中的主张。

将审稿人回复、稿件或补充材料修改，以及对 Ethan 的回复分开处理。以简洁的第一人称撰写给 Ethan 的回复，使用例如 `I revised`、`I clarified` 或 `I added` 等形式。若意见提供了写作策略，简短致谢并说明该策略应用于何处。若他指出某处用词不清，先用平实的语言解释原意，再提供修改后的用词。若他询问为何未呈现所要求的功能，应将原因紧接置于限制或拒绝说明之后。格式检查、确认事项与结尾致谢应简短回复，而非重复科学解释。

当 Ethan 针对敏感度或稳健性检定询问 `so what?` 时，回复必须依序说明：哪些数值结果改变了、哪些具名模式或结论维持不变或改变了、若涉及规格选取问题则正式模型使用了何种设定及其独立依据，以及稿件或补充材料如何呈现该检定。切勿在未重述实质比较的情况下，使用例如 `this finding`、`the ordering` 或 `the conclusion` 等模糊短语作答。

当 Ethan 对 `current`、`revised`、`updated` 或 `original` 的设定提出质疑时，首先确认该短语是指局部定义的整体模型版本，还是隐藏了单因素比较。当两个版本皆有明确介绍时，保留指导教授定义的整体模型标签。对于单因素检定，将标签替换为实际的数值、区间、分布、规则或事件序列。切勿跨越不相关的意见进行全域术语替换。

当需要最终决定句时，将其置于敏感度结果及其意涵之后。在相邻的回复中变换过渡词与句型结构。将稳定的模式或结论视为稳健性的证据，而非基准设定更佳的证明。若所采纳设定的独立依据已确立，应予以陈述；否则应说明敏感度分析并无法决定设定的选择。切勿仅为了让决定听起来更有力而添加新的理由。修改后应更新对 Ethan 的回复，使其报告实际的决定或未解决的选取依据，而非仅仅表示回复已获澄清。

<a id="output-additions"></a>
## 产出增补项目

当此叠加层处于启动状态时：

- 将 `REVIEW PROFILE` 设为 Ethan 风格内部审查
- 重要项目纳入 `MUST / SHOULD / QUERY / PREFERENCE`
- 仅在有先前证据时纳入跨轮次状态
- 以确切的下一轮指示作结
- 说明同时执行了哪些中立的方法与领域模块

当提供有研究团队评分规准时，使用 [review-checklist-and-cases.md](review-checklist-and-cases.md) 进行其适用的代码对应。切勿仅凭封存的范例推断评分规准的确切规则或项目要求。
