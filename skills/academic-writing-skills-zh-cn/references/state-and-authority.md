<a id="authority-hierarchy"></a>
## 权威层级

请建立项目专属的层级架构，切勿假定有一套通用的来源顺序适用于所有研究。实用的默认层级如下：

1. 经核实的原始证据：原始或处理后的资料、分析产出物、方程式、表格、图表、逐字稿、来源语料库或正式核准的元数据
2. 与该证据相扣合的当前研究方法与研究结果
3. 当前的讨论与研究限制
4. 当前的摘要总结：摘要（Abstract）、重点精华（highlights）、结论、研讨会摘要、投稿说明信（cover letter）
5. 仅作为参考之用的历史草稿或相关稿件

当作者指明不同的权威来源时，请推翻此顺序，并将此例外记录下来。

切勿从字体排印、档名、作者顺序、星号、先前的论文或过时的摘要中推论事实。在有来源解决该问题之前，请将其标记为未知。

<a id="managed-project-records"></a>
## 受管项目记录

请维护一份 `manuscript_state.json` 或同等的项目记录，内容包含：

- 项目识别、稿件原型、生命周期阶段与审查成熟度
- 作用中的产出物与历史参考资料
- 权威来源及其处理范围
- 稿件约定：研究缺口、任务、问题或目标、成果、贡献与非主张事项（nonclaims）
- 语意锁定与术语规则
- 语言变体、受保护的专业术语、允许的重复字词以及项目不建议词组
- 附带来源的事实与元数据
- 缺口–问题–方法–证据–主张对齐项目
- 设计维度与报告栏位覆盖率
- 决定与未解决问题
- 发布候选版本与必要检核

以 `assets/manuscript_state_template.json` 作为起点。请将状态保存在稿件项目旁，而非置于本技能内部。

此记录提供的是背景脉络，而非审查处理范围。进行局部工作时，仅须查阅相关的来源、锁定、术语及决策项目；重复使用输入未变更的当前证据。切勿仅因任务只是进行中项目的另一个段落，就重新初始化新记录、重启每个发布检核关卡，或重新开始全篇论文的审查。

请将风格设定档视为项目指引，而非证明每个已登记词组皆属错误的凭据。即使确定性内文审查报告显示使用频繁，仍应保留专业术语与作者核准的措辞。

当项目或投稿管道要求既定的开放式复合词（open compounds）即使在另一个名词之前也必须保持分开书写时，请将其登记在 `style_profile.preferred_open_compounds` 中。内文审查随后会报告已登记的连字号变体，以供脉络审查。

一致使用机器可审查的登录栏位：

- 语意锁定：`id`、`kind`（`EXACT` 或 `SEMANTIC`）、`canonical`、选填的 `required_roles` 以及选填的 `forbidden_variants`
- 术语项目：`id` 或 `concept`、`preferred`、选填的 `prohibited`（审查亦接受旧版 `avoid`）以及选填的 `scope_roles`
- 事实项目：`id`、`value`、`source_id`、选填的 `expected_strings`、选填的 `forbidden_strings` 以及选填的 `scope_roles`

切勿将诸如 `term/rule` 的纯文字提醒存放在 `semantic_locks` 中，随后声称通过了锁定审查。请将其转换为上述纲要结构，或记录为需要手动核实的决策。无法被审查的登录项目必须据实报告，切勿默默略过。

<a id="persistent-terminology-procedure"></a>
### 持久化术语程序

请维护反复出现的构念、具重大影响的指标、缩写及容易混淆的标签，而非每个普通词汇。请将这份单一共用记录保存在论文旁。其既有的 `project`、`artifacts`、`contract`、`facts`、`alignment`、`decisions` 与 `issues` 能提供权威性与延续性；大纲或检核记录可直接参照这些内容，无须复制出第二份清册。

持续写作时，请使用既有的项目记录或同等词汇表作为共用字汇集，切勿依赖对话记忆。将其与当前稿件的身分识别及权威版本绑定。复制的记录或吻合的主题，并不能构成对另一篇论文的权威。对于一次性的修改，作者提供的相关术语可直接保留在内文中；无须强制要求建立新的项目文件。

1. 在动笔前，请阅读相关的已确认概念、定义、偏好术语、明确允许的变体／缩写以及处理范围。辨识出必须保持区隔的概念。在需要处记录定义／来源与确认出处；切勿从不熟悉的标签凭空捏造定义。
2. 在写作期间，请保留已定义概念的名称，切勿轮替使用同义词。作者明确的术语决策或指定的权威定义方可确认某个项目；助理在草稿中的用法则不行。请将新建议与未解决的意涵分开保存（例如存放在 `terminology_proposals`），并注明其来源与理由。若某个项目被明确标记为 `PROPOSED`，在任务重启时切勿将其视为已确认。既有未注明状态的旧项目将维持其既定的扫描行为，而非捏造核准出处。
3. 当出现新词组时，判定其为经核准的变体、独立概念，或可能是命名不一致。仅在未解决的意涵会影响所请求的主张时，才提出幅度最小的修复或进行询问。切勿查禁所有新词组，亦不可将意愿、观察到的行为、福祉及其他独立构念混为一谈。在实际语境中保护引文、文献标题、官方调查工具名称及有效屈折变化；切勿仅因某个词在某处受保护，就将该词设为全局豁免。
4. 在指定的章节边界处，核对新确认的选择与待处理的提议。对于作者核准的更名，在变更之前请先指明受影响的内文、图表展示与附属文件。彼此冲突的已确认决策将维持未解决状态，直到权威解决为止；仅凭时间较新并不代表获得核准。
5. 对照当前记录检查确切的交付成果。在支援时，于审查证据中保留候选文件与状态的杂凑值、规则版本／杂凑值以及已检查的处理范围。变更登录项目、规则、处理范围或候选文件，皆会使相关的先前证据失效，即使段落本身未曾改变亦然。

仅在任务需要术语协调时，空的登录清册才需要对现有权威资料进行有边界的提议扫描；这不会阻碍文法修复。请将已确认的适用项目、未解决的概念与字面扫描结果分开报告。`PASS` 意指没有符合设定的扫描结果，并不代表词汇覆盖完全或语意正确。若产出物角色不明，请揭示该项限制；切勿宣称已获得特定角色的检核许可。当 `--label` 与提供状态中的有效产出物 ID 完全相符时，本机 CLI 即可解析出角色。引号内的相符项仍属脉络诊断性质；指令码并无法判定先前未登记的两种表达方式是否指称同一个概念。

对于已确认的项目，当需要区分意涵时，除了既有的可审查栏位外，请同时保留 `definition`、`allowed_variants` 与 `confirmation_source`。例如，作者的决定可能会确认以 `intention to enroll` 表示自陈的可能性，而保留 `enrollment` 用于观察到的登记情形。这两者并非同义词。建议的替代词应置于 `terminology_proposals` 中，并附带其问题／来源与 `status: PROPOSED`，直到权威解决为止。这些描述性栏位有助于人工／代理的判断；字面扫描并无法验证定义或确认来源。

在工作重启时，请比对论文识别身分与当前有效版本，接着仅读取相关项目与未决决策。在章节交界处，请在同一份记录中核对新确认的决定与仍待处理的提议。定义的变更可能会使比较失效，即使其句子本身未改变亦然；在重复使用旧证据之前，请先指明受影响的研究方法、图表展示、摘要与检核。切勿重启无关的检核。请使用 [execution-and-acceptance.md](execution-and-acceptance.md) 中的阶段程序来记录该边界。

<a id="lock-and-change-rules"></a>
## 锁定与变更规则

仅在使用者已明确定案或必须逐字保留的内容（例如正式的研究问题）时，才使用精确锁定。当措辞可有所变化、但科学任务与处理范围必须维持稳定时，请使用语意锁定。

在变更锁定之前：

1. 解释提议的语意变更
2. 指明受影响的章节与产出物
3. 自使用者或指定来源取得授权权威
4. 记录新决定已取代旧决定
5. 执行适用的影响检核关卡

切勿纯粹为了排比句结构、文体多样性或缩减字数，就变更已被锁定的意涵。

<a id="issue-and-version-states"></a>
## 问题与版本状态

将问题状态记录为 `OPEN`、`RESOLVED` 或 `WAIVED`。豁免必须包含核准权威、原因、受影响的主张以及残留风险。

将严重程度独立于处理范围之外使用：

- `S0`：仅限格式
- `S1`：局部可读性
- `S2`：看似合理的误解或局部不一致
- `S3`：主要论点、可重现性、跨文件或投稿完整性风险
- `S4`：研究问题、证据有效性、主要结论、伦理或正式元数据风险

将证据状态记录为 `CONFIRMED`、`PROBABLE` 或 `UNVERIFIED`。

维护一份作用中的发布候选版本。将所有其他草稿标记为历史记录、已被取代或仅供参考。切勿使用如 `FINAL` 之类的档名作为已准备就绪的凭据。

<a id="minimum-operating-procedure"></a>
## 最低操作程序

1. 找出作用中的文件与相关来源。
2. 重复使用相关的项目状态项目；仅在需要持续协调时才初始化或更新记录。
3. 在相关时执行 `audit_manuscript_state.py` 进行状态验证或整合／发布工作，而非将其作为每次局部修改时强制执行的全新完整状态审查。
4. 解决来源冲突，或将其保留为明确记录的问题。
5. 执行所要求的审查或修改。
6. 更新受影响的状态项目并执行影响检核。
7. 执行功能完整性回顾。
8. 唯有在通过发布检核关卡时，方可认证已准备就绪。

将检核覆盖范围与问题／证据状态分开报告：已检查、不适用、超出请求的处理范围，或来源无法取得／未核实。被排除的产出物既不算通过，亦不会自动成为完成较窄范围任务的阻碍；但这确实会限制任何更广泛的就绪宣称。
