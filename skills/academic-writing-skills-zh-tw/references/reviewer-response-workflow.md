# 審查意見回覆工作流程

此參考資料適用於申辯信（rebuttal letters）與審查意見回覆文件。

<a id="core-rule"></a>
## 核心規則

唯有直接回答審查意見的疑慮，並指明稿件中有明確可見的修改，或是針對未依要求修改提供具證據支持的理由時，回覆才算完整。回覆文件可包含有助於審查人理解、但無須納入稿件或補充資料（Supporting Material）的分析與實作細節。

<a id="build-a-comment-ledger-first"></a>
## 先建立審查意見清單

在起草文字之前追蹤每則審查意見：

```markdown
| ID | Reviewer Comment | Anchor Text | Response Strategy | Manuscript Change | Status |
|---|---|---|---|---|---|
| R1.1 | ... | Section 3.1 | revise model; Figure R1 | revised method | RESOLVED |
```

逐字保留審查人的原始意見。將包含多個部分的意見拆解為具體問題，以免修飾流暢的段落掩蓋了未回答的部分。在回覆策略欄位內記錄子問題與證據，或在複雜修改有需要時新增選填欄位；切勿建立第二套不相容的清單結構。

若先前的某項疑慮已不再適用，請針對該子問題記錄原因，並獨立檢核其餘問題。切勿僅因其中一部分已被取代，就刪除包含多個問題的討論串。單純的回覆、查詢 DOI 或產生的算繪圖，僅能證明已執行該動作，並不代表已完成分析、具備主張層級的支持或已完成視覺檢查。

請遵循稿件狀態的狀態約定：`OPEN` 代表未解決的工作，`RESOLVED` 代表已完成且已核實的回覆，而 `WAIVED` 僅限於已指明的權威接受殘留問題與風險時使用。

針對每項疑慮，在此清單中套用 [comment-scoped-revision.md](comment-scoped-revision.md#test-concern-closure-separately-from-edit-completion) 中的結案評估：原始選定措辭／版本、實際問題、當前答案與已定位的證據，加上已處理／部分處理／未解決／無法核實並附帶理由。這些評估並不會取代前述的狀態。請務必核實答案本身，而非僅確認答應修改的文句已存在；彙總合併的回覆不能用來結案某個仍未回答的獨立子問題。請保留當前工作中的措辭。

將所需工作歸類為下列一或多項：

- 釐清既有的方法或結果；
- 修正錯誤或含糊不清的規格說明；
- 新增或重新執行分析；
- 補充證據或引用文獻；
- 修改詮釋、處理範圍或限制；
- 說明具體理由以婉拒或推遲某項要求。

<a id="distinguish-response-states-and-advisor-handoffs"></a>
## 區分回覆狀態與指導教授交接流程

策略、呈交指導教授的工作草稿，以及最終呈交審查人的回覆，這三者應保持明確區分。策略須指明預計採取的行動與所需證據。工作草稿可在所有修改尚未齊備前先行鋪陳預定論點，但必須標示待進行的分析、修改與定位點；擬議的措辭不能作為已完成的證據。最終回覆僅報告已核實的工作或具證據支持的不作修改理由。在該疑慮確實獲得處理並經核實之前，清單狀態應維持為 `OPEN`。

當研究室提供的工作流程要求「先回覆後由指導教授審查」時，請遵循其交接順序：審查意見清單與簡要策略 → 指導教授同意 → 回覆工作草稿 → 指導教授審查 → 經授權的稿件／補充資料修改 → 最終答應事項與產出物對照及定位點核對。這是可選的專案工作流程，並非要求在編輯前必須取得指導教授核准的普遍通則。策略的獲准本身並不代表已授權可執行新分析或外部行動。若範本偏好工作草稿使用現在式或過去式，請明確標註尚未完成的內容，切勿將未執行的實驗呈現為已完成。

<a id="distinguish-revision-provenance-from-topical-relevance"></a>
## 區分修改出處來源與主題關聯性

在新增標註審查人來源的邊頁註解或宣告稿件修改之前，請將實際生效的修改文字與當初實際投稿的稿件或其他明確約定的修改基準進行比對。請閱讀實際生效的修改文字（保留的文字加上新插入的文字），切勿將已刪除或移出的文字串接進來。

將每段候選文本分類為未變更、新插入、已替換、已移動、純格式變更或已刪除。僅針對確實因回應該審查人而修改的文字、圖表展示或位置，新增標示審查人來源的標籤。邊頁標籤是用來記錄修改的出處來源，並非主題索引。未變更的原始文本或許可支持回覆論點，但應維持不加標籤，並在清單中記錄為 `existing text; no manuscript change`。回覆可引導審查人參閱該既有段落，但不可聲稱該處有修改。

若審查人對未變更的措辭感到困惑，請判定既有段落是否已回答該疑慮。若是，請進行解釋並加以引用；若否，請進行幅度最小但充分的修改，並將標籤錨定在該修改處，而非整個周邊段落。當單一修改同時回應多則意見時，請使用一個註解方塊列出適用的審查人 ID，切勿在相鄰位置重複放置標籤。

對於基於模型或計算的研究方法，請將定義與衍生量，與經驗輸入值、校準參數、文獻支持或分析者自選的假設，以及演算法或更新規則明確區分開來。對於其他研究設計，請依其實際的方法學功能對段落進行分類，例如抽樣、測量、介入措施、程序、編碼或分析。切勿僅因某個定義或衍生結果與假設並列，就將其視為假設。請讓回覆主張、相關清單項目、修訂追蹤（Track Changes）與審查人標籤，與實際變更的功能保持一致。僅在修改確實需要此項區分時，才在清單中新增選填的來源或出處欄位。

<a id="distinguish-navigation-from-the-full-answer"></a>
## 區分導引說明與完整回答

審查人有時會在列出編號的主要意見之前，先提供高層次的統整觀點。

- 高層次的回覆應保持精簡：確認問題所在、陳述主要處置，並引導讀者參閱下方的詳細回覆。
- 將第一個完整的解釋、設計、證據與結果，放在最早提出該問題的詳細意見下方。
- 將審查人的每條詳細意見視為可獨立閱讀。後續相關的回覆必須包含足夠的局部脈絡、關鍵結果及其意涵，以回答該項特定的疑慮；此處可回指前文的完整的共用設計、圖或表，無須重複列出該證據。
- 切勿讓前面的詳細回覆仰賴後面的審查意見回覆。指向後文的參照（forward reference）僅適用於前言導引區塊。

<a id="build-opening-and-closing-responses"></a>
## 建立開篇與結尾回覆

在開篇的修改摘要中，每一點應賦予單一功能。請將研究或模型的變更、補充分析、文件修訂及圖表展示更新分別列出，切勿在多個標題下重複提及同一項修改。若回覆範本要求提供導引資訊，可指明是哪位審查人或編輯促成了該項變更，但請將完整證據保留在相關的詳細意見下方。

將審查人結尾的總體評估視為獨立的意見。當該意見無須採取額外行動時，簡要致意確認即可，切勿重複前述的修改摘要或已列出的證據。

<a id="draft-a-major-response-in-this-order"></a>
## 依此順序起草主要回覆

在維持此推理順序的前提下，使用最少必要段落數：

1. **肯定並理解審查意見的疑慮。** 簡要說明該意見為何指出了重要問題或契機。
2. **陳述修改內容與原因。** 指出有所變更的方法、模型設定、分析或詮釋。在修正規格時，請說明其不一致之處，切勿讓人覺得微調參數純粹是為了取得屬意的結果。
3. **說明執行的程序。** 提供足夠細節以供審查人評估該工作，包含在論文中無須贅述的重要細節。
4. **陳述工作處理範圍。** 若修改需要完整重跑模型、重新產製圖表或重複進行分析，請明確說明。
5. **呈現已核實的證據。** 在列出數據之前，先提供詮釋該數據所需的統計特性與比較基準。在相關處提供分母、參考值、不確定性摘要或對齊的設定。
6. **詮釋結果。** 切勿在報告數據或描述圖表後便戛然而止。請說明何者改變、何者維持穩定，以及該證據如何回應審查意見的疑慮。
7. **指明稿件修改處。** 列出實際修改的章節、圖、表或補充資料項目。唯有在指定的審閱版稿件及其排版格式底定後，方可使用最終行號。
8. **在重大限制存在時說明殘留邊界。** 說明本研究仍未涵蓋哪些層面並說明原因。切勿僅以空洞的 “no.” 作答。

開篇的肯定與理解應保持簡短。切勿在說明作者做了哪些修改或回覆為何採取不同立場之前，長篇累牘地轉述審查人的意見。

若是簡短的釐清或錯字更正，請將此流程壓縮為一至兩句話，切勿捏造不必要的細節。

當包含多個部分的意見同時需要條件說明（qualification）與採取行動時，請在轉移重點之前先完整回答需說明之處。接著使用明確的轉折詞，例如 “However, we agree...” 或 “Following the reviewer’s suggestion...,”，以指明作者接受的部分以及所執行的具體分析或修改。如此可在謹慎辯明之後突顯具體的回應行動，但絕不可因此轉移焦點、取代或遺漏對該意見第一部分的回答。

<a id="match-response-length-to-the-scientific-weight"></a>
## 讓回覆篇幅與科學份量相稱

若審查意見引發了模型重新設計、採用新資料集、新增分析或完整重跑，其回覆的完整程度應至少不下於該審查意見，且篇幅通常應相當。請將篇幅長短視為警訊（提醒可能遺漏了原因、實作細節、證據或意涵），絕不可作為重複內容或充填無關字句的理由。請在不讓回覆變成第二個研究方法章節的前提下，突顯所付出的額外工作。次要的編輯性意見無須刻意擴充篇幅。

針對重大的模型或分析變更，若僅供回覆用的表格或圖形能讓審查人迅速驗證效果，可考慮採用。唯有在該圖表能直接分離出受到質疑的因素，且立基於當前模型與證據時，方可使用。切勿純粹為了讓回覆看似內容充實，就納入混雜多個同時變更的比較，或是依賴過時的產出結果。

<a id="present-numbers-without-creating-a-new-vulnerability"></a>
## 呈現數據且不製造新的漏洞

- 當讀者需要分母或比較基準值以進行詮釋時，為每個絕對誤差或計數提供該分母或比較基準值。
- 在呈現可能造成誤導的指標之前，先說明資料覆蓋率、分析單位、地理尺度不相符或其他統計限制。
- 對觀察到的數值使用中性描述。避免給出 “the model fails,”、“weak agreement,” 或 “overall overestimation” 等定論，除非該結論具備證據支持且屬必要。
- 指出具科學相關性的訊號（無論有利或不利），但不可做出超出證據支持的倡議或主張。
- 無須向專家解釋標準指標，除非其定義為本研究特有；應改為解釋這些數值對本次分析代表的意義。
- 將絕對值診斷指標與標準化時間序列比較區分開來，並說明各自回答了哪個問題。
- 在陳述每項比較結果的同一個句子中指明比較基準。若讀者必須自行推敲比較的基準設定、組別、時間或情境，則像是 `higher`、`lower`、`increased`、`decreased`、`remained` 或 `unchanged` 等詞彙便是不完整的。
- 切勿僅從參數值、分佈、規則或模型設定之間的敏感度比較，推論某個情境相對於另一情境的效果。不同設定之間的差異並不能證明個別情境對比的效果，除非該對比經過直接計算。
- 報告圖表的第一個數值結果時即應引用相關圖表。挑選能回答審查意見的最少必要數值組合即可，無須逐一敘述表格中的每個儲存格。

<a id="explain-sensitivity-and-robustness-results"></a>
## 解釋敏感度與穩健性結果

敏感度分析的回覆必須指明：

- 受到質疑的假設；
- 以淺白語言說明的當前設定與替代方案；
- 維持不變的條件；
- 用於判定敏感度的結果指標；
- 結果的方向與量級；
- 相關詮釋是否有所改變；
- 當涉及規格選擇爭議時，正式模型中採用了哪種設定，以及該選擇的獨立依據；以及
- 該結果在何處報告。

將每項敏感度回覆依「**原因 → 內容 → 比較 → 結果 → 意涵**」來組織。若審查人明確要求進行檢定，請說明所選設計如何回應此要求。若審查人未明確要求檢定，請先解釋受到質疑的假設為何可能影響報告的結果，以及為何額外的檢定具有參考價值。接著指出進行比較的確切設定或組別，以及用於判定影響的結果指標。絕不可在未說明目的的情況下引入實驗。

在結果與詮釋部分，應以明確的證據鏈作結：說明估計量級是否改變，並指出具體有哪些模式、詮釋或結論改變或維持不變。切勿僅寫 `the conclusion was unchanged`；請陳述結論本身。

當檢定或審查意見提出規格選擇問題時，請另行加入一項決策聲明，指明正式模型中所採用的設定及其既有確立的依據，例如資料、校準、理論、研究設計或預先指定的建模選擇。若發現替代設定不改變主要結論，這證明的是穩健性，其本身並不能用來挑選或驗證基準設定。若缺乏獨立的選擇依據，請說明敏感度分析無法決定應採用何種設定。切勿在看到敏感度分析結果後，才事後捏造新的經驗、理論或實務理由。若該分析純粹為了檢驗穩健性且不涉及規格決策爭議，切勿強加模型選擇的主張。

在實際受測的層次上指明比較的設定。在單因素實驗中，請使用確切的基準值、區間、分佈、規則或序列。將 `original model setting` 與 `revised model setting` 等標籤，保留給各版本皆有明確描述的局部定義全模型比較。切勿僅因同一詞組在單因素敏感度檢定中顯得含糊，就全面替換已具備定義的全模型標籤。

當需要做出最終模型決策時，請將其置於結果及其意涵之後，並在指明稿件或補充資料的安放處之前。讓句子自然承接前述證據，切勿在每則回覆後都附上千篇一律的套版轉折語。當單一回覆彙總了數個敏感度實驗時，在每個實驗皆獲得各自的局部結果與意涵後，可使用句結尾語列出所有最終設定及其既有依據。個別的詳細回覆仍必須陳述任何局部相關的決策，以便每則意見都能被獨立閱讀。

在呈現證據之前，請於回覆內文中先提供詮釋圖表所需的資訊。這包含比較基準、變更的因素、在重要時標明比較的次數、不確定性摘要，以及正負差異所代表的意義。表格註記應維持精簡，且僅用於緊湊而自成一體（self-contained）的細節；切勿將實驗設計、比較邏輯或實質詮釋隱藏在註記之中。

在報告圖表中的第一個數值之前，先加上一句直接陳述的話，說明該圖表比較了什麼、報告了哪些結果指標，以及數值如何彙整。標題應明確點出結果指標與比較基準；像是 “sensitivity results” 或 “comparison” 的標籤是不夠的。請使用內文（而非圖表說明或註記）來解釋為何進行這項比較以及結果代表什麼意義。表格註記應嚴格限制於閱讀各項目所需之資訊，例如單位、分母、摘要統計量、不確定性標記法或正負號的意涵。

依審查人的問題選擇證據呈現格式。若要緊湊比較終點數值或多項精確對應關係，請使用表格；若疑慮涉及順序、時序、軌跡或路徑相依性，請使用時間序列圖。對於相同的數值，除非圖與表各自回答了該意見的不同部分，否則切勿同時納入兩者。

回覆內文與圖說明應保持區隔。在內文中，用一句話引導出科學比較、報告結果，並針對審查人的疑慮解釋其意涵。除非某種視覺編碼本身就是論點的一部分，否則切勿引導讀者逐一檢視子圖代號、顏色、線條樣式、標記或區間帶。子圖配置、視覺編碼、樣本數或執行次數以及不確定性定義，應放在圖說明或圖例中。圖說明結構與術語應與稿件既有風格相符，切勿自創一套僅用於回覆的圖說明風格。圖說明應解釋如何讀圖；內文則應解釋該圖在科學層面呈現了什麼。

將所採納的基準模型規格與敏感度檢驗程序明確區分。純粹檢驗穩健性的敏感度檢定若未改變模型規格或主要詮釋，切勿將其作為所採納模型研究方法的一環來呈現。研究方法章節應聚焦於所採納的規格、校準與假設。當敏感度結果對一般讀者甚為重要時，在相關結果段落的末尾加上一至兩句話說明其影響。當延伸證據置於補充資料時，自該段落引導讀者參閱補充資料；其餘情況則將證據保留在回覆信中。請明確陳述所選的安放位置，切勿在所有位置重複相同的細節。

切勿使用內部實驗 ID、未經解釋的標籤（例如 “higher” 或 “narrower,”），或審查人未曾見過的軟體術語。請指出實際的參數區間、規則、分佈或事件序列。

當有多則意見涉及同一個實驗時，請在第一個實質提及處給出完整的設計與證據。後續的回覆仍必須說明當前的局部目的、關鍵結果及針對該意見的具體意涵，但可引用先前的圖或表來指涉共用的設計與完整證據。

<a id="separate-three-destinations"></a>
## 區分三個安放位置

每則回覆皆應區分以下三者：

1. **僅限回覆：** 回答審查人所需、但一般讀者無須了解的診斷性證據、比較表格或實作細節。
2. **稿件正文：** 為了方法透明度、結果詮釋或主要結論所必需的修改。
3. **補充資料：** 可重現性細節、延伸方法、完整技術結果或作者選擇提供的研究工具。

正文表格與相關的補充資料表格應具備不同的讀者功能。正文表格應承載跟隨論文論點或模型所必需的資訊，而補充表格則提供出處來源、實作細節或延伸證據。切勿僅為了顯得有正面回應，就在兩處重複列出相同的項目。

切勿純粹為了顯得樂於配合，就答應在稿件或補充資料中增補內容。在修改尚未實際完成前，切勿聲稱修改已經完成。在規劃階段，請使用未來式或明確標示擬議措辭。在最終回覆信中，核實指定檔案後，針對已完成的修改應使用過去式；現在式則可用於描述當前的證據或文件內容。

<a id="tone-and-vocabulary"></a>
## 語氣與詞彙

- 當審查意見帶來了有意義的修改時，展現專業的謝意，但切勿以千篇一律的公式化句型作為每個段落的開頭。
- 寫作時請設想審查人雖理解論文的大致研究方向，但可能不清楚模型內部的運算順序、專案特有術語或先前的起草歷程。請在首次使用時解釋每個必要的術語、比較與因果步驟，切勿預期審查人能自行拼湊理解。
- 開門見山給出答案，隨後附上證據與稿件修改處。
- 使用稿件中已有的術語。當讀者可能未曾見過某個縮寫時，在該審查人回覆章節中首次出現時加以定義。
- 立即定義本研究特有的術語；若有助於將其與既有既定術語區分開來，首次使用時請加上引號。
- 避免自創複合標籤、諸如 “the revised design,” 的含糊參照，以及未加解釋的內部簡稱。
- 偏好主詞與動作明確的質樸語句。變換轉折詞，使相鄰段落讀起來不致像是斷開的條列句或重複的 “We...” 陳述。
- 切勿誇大完成度、穩健性、驗證程度或泛化能力。

起草完成後，請大聲朗讀完整的回覆，或模擬一般口語朗讀。請保持技術意涵精確，但若有任何句子聽起來像是生硬拼湊而非研究者自然寫就、需要反覆回讀才能理解，或是會讓目標審查人困惑於其主詞或比較對象為何，皆應予以修改。

<a id="revise-an-advisor-edited-response-draft"></a>
## 修改經指導教授審訂的回覆草稿

將最新經指導教授審訂的文件視為工作基準。保留指導教授可用的修改，且僅變更被標註出的問題、經核實的事實相依處，或是上下文仍不清楚的措辭。切勿僅因較舊的草稿包含較多細節，就依據舊草稿重新建構回覆。

針對有定錨的指導教授註解，在提出修復前，先使用 [comment-scoped-revision.md](comment-scoped-revision.md) 閱讀其當前所選範圍與完整討論串。保留未被選中但可用的措辭；報告確切修改的句子以及超出該範圍且有證據支持的相依變更。內部回覆或標記為已解決是獨立的動作，並非修改內文時的自動環節。

將三項產出物分開：呈交審查人的回覆、稿件或補充資料中對應的修改，以及給指導教授的內部回覆。給指導教授的內部回覆請以精簡的第一人稱撰寫，通常為一句以具體行動開頭的話，例如 `I revised`、`I clarified` 或 `I added`。僅在指導教授提出疑問或表示困惑時，才解釋原始意圖。當指導教授提供寫作策略時，簡短致意該項建議並指明應用於何處。常規格式調整、確認事項與結尾意見僅需簡短回覆即可。

修改回覆內文後，請重新閱讀指導教授的註解並更新內部回覆，使其準確描述實際進行的修改。當修改同時改變了比較、詮釋、最終模型決策或文件安放位置時，切勿留下僅寫著 `I clarified` 的過時回覆。

<a id="disagreement-or-an-unimplemented-request"></a>
## 意見不一致或未採納的要求

在有證據支持的前提下，表達不同意見是可接受的。請採用此結構：

1. 理解並肯定審查意見的疑慮；
2. 陳述證據、資料邊界或學界慣例；
3. 解釋所要求的實作方式為何站不住腳或不可行；
4. 在存在的情況下，提供最接近的有效分析或釐清說明；以及
5. 說明由此產生的限制或未來研究方向，但不可將其用作替代當前答案的託辭。

切勿在沒有立論支持的情況下寫入 “we respectfully disagree” 或 “this is outside scope”。切勿純粹為了顯得有正面回應，就加入無法被一致呈現的不完整機制。

<a id="contradictory-reviewer-requests"></a>
## 互相矛盾的審查意見要求

當審查人要求彼此不相容的修改時：

1. 在工作清單中明確標出衝突；
2. 優先考慮編輯的決定、期刊處理範圍、研究證據與內部一致性，而非機械式地試圖同時迎合雙方要求；
3. 在兩位審查人的回覆中皆解釋所選用的做法，使任一回覆都不致顯得忽略了另一方的疑慮；以及
4. 當衝突若不改變研究的科學處理範圍就無法解決時，在投稿說明信（cover letter）中請求編輯指引。

<a id="formatted-response-documents"></a>
## 具格式排版的回覆文件

當交付成果為 Word 格式的回覆文件時：

- 逐字保留審查人意見及其原有文字顏色；
- 保留回覆顏色、修訂追蹤、邊頁註解、版面設定以及研究室既定的範本；
- 一致地格式化僅供回覆用的圖表標籤；
- 依最終首次引用的順序，為僅供回覆用的圖表編號，隨後一致地更新每處交互參照；
- 將參考文獻保留在文件的既定位置；
- 在算繪產出後，核實跨頁的意見回覆區塊、分頁表格、圖表說明、方程式與圖表；以及
- 唯有在指定的稿件版本及其排版格式底定後，方可填入行號預留位置。

使用現有的 `docx` 或 Word-document 技能來執行修訂追蹤與 OOXML 操作。

<a id="promise-to-artifact-reconciliation"></a>
## 答應事項與產出物對照核對

進行修改套件檢核時，請從雙向進行檢查：回覆中答應的每項承諾，皆必須指向已實作且已核實的修改，或提出具充分理由的不修改說明；而稿件／補充資料中的每項實質修改，唯有在直接回應某項審查意見時，才應報告於該意見之下。切勿將每處編輯性改動都轉化為新承諾、切勿在未變更的文本加上主題標籤，亦不可默默將未兌現的承諾標記為已解決。當缺少必要的補充或分析時，請保留該未解決問題。寫作審查並不代表已授權可重新執行模型。

追蹤實際的安放位置與變更的功能。初始化、年度更新、決策門檻與執行機制各有不同；支持其中一項的證據不能用來確立另一項。請檢查重要假設是否置於研究方法中，而非僅在研究限制中披露。支持制度論理的文獻來源不能用來估計數值門檻。橫斷面調查證據無法驗證同一個人隨時間的年度變化。對於非機率樣本，切勿將簡單隨機抽樣的誤差範圍呈現為該樣本已證明的精確度。請在重複執行所實際衡量的層次上描述其不確定性。

區分來源比較與直接驗證。地理涵蓋範圍、抽樣單位、納入標準與分母必須相符或加以限定：每筆已理賠賠案的平均值不等於所有家戶的平均值，且某區域的紀錄不必然是模型建構領域內的觀測值。請說明診斷指標實際評估的內容；切勿暗示記錄了此項不符便全盤推翻每個組件，亦不可暗示模擬出的軌跡即為實際觀察到的登記註冊情況。

在重新調整圖、表、章節或補充資料後，請依其用途逐一核實每處參照，包含子圖代號、圖表說明、清單、縮寫選擇以及相關的回覆承諾。請與稿件中實際保留的術語保持一致；若某個縮寫已被移除，切勿聲稱有使用該縮寫。檢查引用文獻是否與所支持的子句及參考文獻清單相符（包含作者與年份後綴）。在刪除某篇參考文獻前，請先檢查其在其他地方的引用情況。新增引用文獻必須具備主張層級的支持，而非僅憑標題相關或希望引用近期著作。

為回覆定位點選擇並記錄算繪出的目標版本。依交付合約，該版本可能是乾淨版稿件，或是比對／標記版稿件；絕不可從 XML 段落計數推算行號，亦不可沿用其他版本或標記檢視模式下的行號。在讀取顯示的行號前，請先凍結內文、版面設定、行號配置與顯示模式。若分頁發生變動，請重新檢查受影響的範圍，切勿認定微小修改不會產生影響。對於未編行號的補充資料，請引用其 Text／Figure／Table 項目編號；切勿套用正文行號或留下最終 XX/XXX 預留位置。當目標無法算繪時，請將定位點標記為未核實，切勿憑空猜測。

以獲接受且經指導教授審訂的基準為基礎，衍生出修改後的回覆。若要求提供乾淨版與比對版的回覆版本，請將該基準清理乾淨，並將已核實的最終修訂版本與之比對，同時保留審查人文字與必要標籤。請檢查實際生效的修改文字與算繪產出物，而非串接了刪除／插入文字的草稿。在宣告整套投稿文件準備妥當之前，請確實報告已檢查了哪些項目。

<a id="checks-after-a-model-or-evidence-revision"></a>
## 模型或證據修訂後的檢核事項

這些檢核事項旨在解決當模型修訂同時改變了數據與結果解釋時常見的反覆出錯問題：

- **先鎖定當前證據。** 指出每個結果背後的來源版本、配置與產出物。舊圖表或已完成的實驗不會僅因其標籤仍與意見相符，就成為當前有效證據。
- **區分方向、量級與機制。** 某個組別可能仍維持較大比例的損失減少，但產生該減少過程的機制可能已改變。切勿將此概括為 “the conclusions are unchanged.”。請精準陳述何者維持不變、何者必須重新詮釋。請區分絕對損失、百分比減少，以及相對於所得或其他分母的損失。
- **切勿將多項合併修訂歸因於單一因素。** 數次模型變更後的結果呈現的是其合併效果。若要主張是其中一項變更造成了差異，需要適當的控制比較或其他支持證據。決策規則所提示的機制，並不能自動視為對觀察到的效應大小之測量解釋。
- **將假設、校準與驗證明確區分。** 文獻或許可支持某個方向，但無法支持確切的區間或初始比率。請誠實標註建模者自行選定的數值。唯有存在校準程序與目標時，才稱該數值為經校準，且切勿將同一個目標視為獨立驗證。門檻或指派機率本身並非觀察到或實現的採納率。
- **對齊比較群體與定義。** 檢查地理區域、年份、家戶組別、分母以及事件或政策定義。切勿在未解釋差異的情況下，將某子群體的模型估計比率與全體人口基準進行比較。相對於絕對誤差而言較小的帶正負號誤差可能反映了相互抵消，其本身並不能證明集中趨勢準確。
- **對模型涵蓋範圍的主張保持嚴謹克制。** 新增某項屬性並不意味著模型涵蓋了所有相關的危害、行為、制度或定價關係。請解釋哪些計算確實使用了該屬性，以及哪些相關性仍未呈現。
- **核對事實，而非僅潤飾措辭。** 對照原始紀錄核實樣本數與特定分析的排除項目。切勿純粹為了表面一致而強行讓不同的有效樣本數一致，亦不可將未核實的修正描述為已完成。
- **閱讀實際生效的修改文字。** 檢視修訂追蹤時，請將保留與插入的文字與刪除的文字區分開來。切勿將兩個版本串接在一起，並把由此產生的重複內容當成當前內文來診斷。若因現行檔案無法讀取而使用了存檔副本，請明確指明。
- **避免不必要的擴充。** 賦予摘要要點不同的功能，例如模型變更、敏感度證據、文件修訂與圖表更新。切勿純粹為了增加回覆篇幅而新增實驗、圖表或稿件段落。一項完整的方法學修正可能完全不需要比較圖，特別是當現有的比較會混淆其他變更時。

<a id="common-failure-modes"></a>
## 常見錯誤模式

- 僅說 “clarified” 卻未展示具體修改了什麼。
- 報告數據卻未解釋其與審查意見疑慮的關聯性。
- 在令人意外的指標已被定調為失敗之後，才提出研究限制。
- 僅重述原始文本而非進行修改。
- 將受到質疑的主張移至補充資料卻未正面回答。
- 微調參數以符合預期產出，卻未宣告校準目標與獨立證據。
- 在讀者讀到後續回覆之前便向前參照該處。
- 在模型基準變更後，仍使用舊有的分析。
- 新增未能分離出受質疑因素的圖表。
- 新增無法支持該主張的引用文獻。
- 明明只有回覆做了變更，卻宣稱稿件或補充資料已有修改。
- 拒絕某項要求卻未解釋原因或未提供有效的替代方案。

<a id="final-checks"></a>
## 最終檢核
