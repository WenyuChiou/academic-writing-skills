# 初稿執行與交付驗收

在**首次**交付實質段落或格式化產物之前，即應使用此程序，而非僅在作者發現問題後才執行。它旨在將現有的完整性檢核關卡具體化，並未增加固定的文章架構或新的科學標準。單憑語言掃描絕不代表章節驗收合格。

<a id="select-the-stage-checklist"></a>
## 選擇階段檢核清單

請綜合考量行動、要求的單元、變更影響與可用來源。同一共享的專案狀態提供了術語、事實、決定與未決問題；以下是該項工作的不同檢視面向，而非五本新的紀錄冊。現有的大綱或寫作約定若仍與當前的證據相符，即可作為計畫依據。

| 檢核點 | 執行項目 | 保留或參照內容 |
| --- | --- | --- |
| 大綱／章節規劃 | 指出讀者必備先備知識、段落功能、證據位置、推論界線與橋接句。將各段主題句通讀為一條連貫論點。對於現有大綱，請檢查其實際功能，切勿虛構更理想的過程。 | 功能順序與證據需求；缺乏支持的結果仍列為需求。適配於概念性、質性與其他研究設計，不強加 IMRAD 架構。 |
| 段落起草／實質重寫前 | 確立功能、主張、證據、推展與橋接句；在著手措辭前先排列句子順序並檢查可用的相鄰文字。 | 精簡的寫作計畫或相關現有大綱／約定的定位標記。純文法修復需保留原意，無須擬定新計畫。 |
| 編輯後交付 | 使用以下適用的檢核項目檢查確切的候選文本；將其與計畫、原意、來源及相鄰行文進行比對。 | 候選對象／版本、具體定位的發現、解決方案與剩餘限制。一次性的對話編輯可直接內嵌記錄。 |
| 章節結尾 | 通讀全章的各段開頭與結尾；檢查其解答以及生命週期指南中與研究設計相關的盲點。核對已確認術語、提議、決定與未決問題。 | 實際發現的章節摘要、選定診斷檢驗及其證據界線，以及對共享詞彙的變更或確認維持原狀。 |
| 全文審查 | 完成四輪檢驗：論點／結構、證據／處理範圍、學術寫作、交付完整性。僅在屬於處理範圍內或被觸發時，才檢查受影響的附屬產物。 | 各輪檢驗分別定位的結果與功能完整性回顧。切勿以一次無問題的語言掃描取代全部四輪檢驗。 |

在撰寫新行文之前，請先記錄起草前計畫；切勿事後補記筆記並宣稱這確立了該順序。純審查任務僅評估現有文字，不需要假裝執行了起草前計畫。對於小節／章節的實質工作，請在該單元內執行四輪檢驗，而非無關的章節。全文件的標點符號檢核依然不能等同於科學性的全面審查。

日常的交付請保持簡短：通常只需說明檢查／變更了什麼以及具體的剩餘限制即可。在章節／全面審查的交界處，請擴充記錄，讓下一輪可以重複使用既有決定並找出未解決的項目。切勿詳述每一對句子的檢查過程，亦勿為每個段落單獨建立檔案。「無問題」的結果仍應指出具體段落與實際檢查的內容；千篇一律的保證並不是證據。無法取得的來源仍應標記為無法取得，而非合格。

<a id="before-writing-agree-on-the-readers-route"></a>
## 著手寫作前：就讀者的閱讀路徑達成共識

重複利用現行的約定與來源。指出讀者可能具備的知識、所比較的單元、段落功能以及最低限度的先備條件。針對章節工作，請在起草前寫下簡短的功能順序：確立了什麼、接下來增加了什麼，以及該順序回答了什麼問題。針對有界限的個別段落，僅需檢查現有的相鄰文字。切勿默默捏造缺漏的背景脈絡，亦勿因局部修改而強行全面重寫整篇論文。

對於研究摘要的實質修訂，在動筆措辭之前，請先使用 [conclusion-and-abstract.md](conclusion-and-abstract.md) 中的研究定位準備。找回當前的研究目的與各個研究組件的角色，包含比較單元／維度／層級與相關的處理範圍；重新利用現有的段落計畫。研究目的與用以達成該目的的方法或資料集不可相互混淆。作者已鎖定的段落順序決定了研究定位、研究發現與延伸檢驗各自的歸屬。這不會被純表面修改中的章節關鍵字所觸發，也不需要作者重複目前「引言」（Introduction）中已有的背景脈絡。

在展開從屬細節之前，請先確保主要比較清晰可見。若作者要求進行人類與大型語言模型的比較，請在介紹個別大型語言模型之間的差異之前先引出該項比較。在其他研究中，主要對照可能是處置、區域、理論或時期。**「人類優先」是個別專案的選擇，並非普遍通用的規則。** 定義與專門術語必須在讀者需要之前呈現；解釋它們的作用，而不僅是展開縮寫。

對於圖表展示，在撰寫圖說明之前請先分配好資訊：

- 圖說明：展示了什麼，以及獨立解讀該圖所需的關鍵要素。
- 正文：有證據支持的發現、比較、詮釋與下一步。
- Methods／補充資料（SM）：延伸程序、挑選規則、設定或診斷檢驗。

從圖說明中移除重複的程序，但若省略會誤導讀者，則請保留關鍵的樣本／運行慣例、不確定性定義、分母或排除條件。切勿強制實施通用的圖說明字數限制。

對於流程描述，請對整個要求的單元及其受影響的相鄰文字套用 [workflow handoff test](prose-and-citation-editing.md#workflow-handoff-test)，而非僅針對加上註解的片語。請保留清晰且已被接受的文句與科學意涵；這不會觸發無關的全篇論文審查或額外代理人。

對於錨定修訂，在起草之前請使用 [comment-scoped-revision.md](comment-scoped-revision.md)。綁定目前的來源雜湊值、生效的選定措辭、完整討論串與要求的行動；閱讀周圍行文但切勿解除其鎖定。事後比對來源與候選文本，指出實際變更與未變更的句子，並為任何最小限度的擴充找出證據。檔案編輯、回覆與結案處置應分別取得授權。不確定或過時的錨點不能視為通過處理範圍檢核；選取範圍外的零差異不能作為破壞依賴關係或缺乏答案的藉口。

<a id="before-handoff-perform-then-record"></a>
## 交付前：先執行，後記錄

對於意見導向的工作，請使用現有的 [comment-scope procedure](comment-scoped-revision.md#test-concern-closure-separately-from-edit-completion) 分別記錄編輯完成與疑慮結案狀態。在目前的閱讀單元中定位原始問題的答案，或指出仍未回答／未核實的部分。無問題的措辭掃描、選取範圍的變更或精確的差異對照皆不代表該項判定。請重複利用現有的發現或紀錄冊；不需要新的結構描述、固定的句型或全篇論文稽核。

在完成最後一次編輯後，請檢查**確切**的候選文本及其受影響的依賴項。針對每項適用的檢核記錄一筆已定位的發現；勾選標記或千篇一律的保證並非檢核已執行的證據。現有的專案筆記即可容納這些記錄。對於局部的對話編輯，簡潔的內嵌記錄已足夠；切勿僅為了修改一個句子就建立專案狀態或 JSON 檔案。

| 檢核項目 | 必要行動與驗收證據 |
| --- | --- |
| 意涵與證據 | 將候選文本與已確認且不可擅改的決定之原意及來源證據進行比對；定位任何變更的主張或引文。對於純文法工作，請保留未變更的已核實支持內容，切勿宣稱進行了全新的文獻稽核。 |
| 語言掃描 | 對這些位元組執行適用的術語／套話檢核，並解決或明確保留每一項脈絡發現。掃描的 `PASS` 僅涵蓋該次掃描。 |
| 讀者通讀 | 在首次交付之前，以及後續任何實質行文編輯之後，請由了解廣泛領域但不熟悉本研究內部速記的跨領域知情讀者進行通讀（或模擬冷讀）。對於實質的段落或章節工作，請檢查**每一對相鄰句子**：說明下一句增添了什麼以及為何承接前一句，接著指出文本中能讓讀者建立該連結的證據、比較、指涉對象或先備條件。檢查不明確的主體、專業術語、比較與指涉對象。若無法在不依賴隱藏專案歷史的情況下從段落轉述其關係，請修復順序、內容、指涉或限定條件；刪除多餘的句子可能是最小修復方式。單純添加轉折詞並非修復。切勿強求每句之間都必須有明確的連接詞，亦勿純粹為了句型變化而重寫必要的專業術語重複。接著轉述該段落能讓讀者得出什麼結論。在可行時，真實的獨立冷讀者對複雜章節或重複出現的理解失敗很有幫助；切勿憑空捏造。 |
| 推進與鋪陳 | 對於實質工作或章節／投稿文件，請依序通讀各段開頭與結尾。記錄每個段落增添了什麼以及每個邊界處的實際關係。修復重複的功能、跳躍以及偏離作者鎖定之比較的情況；單純添加連接詞無法修復邏輯。 |
| 研究限制定位 | 當研究限制屬於處理範圍時，請將資料、指標、測量、模型或研究處理範圍中的選擇、不確定性或設計邊界，與可修正的錯誤或遺漏的必要工作區分開來。對於真正的研究邊界，請指出有據可查的來源或條件、其所導致的不確定性，以及所限制的具體結果或推論。在描述不確定性之前請先加以查證；切勿推斷偏誤方向或宣稱論文有缺陷。請修正可修正的錯誤，或準確回報未解決的必要工作，切勿將其重新標記為研究限制。 |
| 圖說明分配 | 當圖表展示／圖說明受到影響時，請將每則圖說明與其對應圖形、正文以及 Methods／SM 進行比對。定位保留的關鍵要素與移除的冗餘內容；重新檢查分圖對應、統計數據與引用標記。 |
| 最終排版 | 編輯格式化檔案時，請依預期尺寸檢查儲存後的渲染效果：圖說明位置、間距、分頁符號、圖形位置、易讀性與重疊情況。驗證直接格式化與繼承的樣式；除非有經查證的規則或作者要求做出變更，否則請保留正常運作的基準。XML、DPI 與來源影像檢查並不能保證嵌入後的排版無誤。 |
| 編輯者身分 | 對於格式化編輯或中繼資料變更，請根據**新**修訂／意見／回覆作者與適用的檔案屬性，查證明確預期的身分。保留歷史作者與意見；切勿將所有人重寫為目前作者，亦勿從助理／模型名稱推斷身分。 |
| 發表場域依據 | 當套用發表場域指定的格式時，請指出載明日期之官方要求、作者／專案偏好或觀察到的範例。切勿將局部的間距或圖說明選擇冒充為期刊的強制要求。無法取得的官方指南仍維持未核實狀態；暫行格式可在無合規認證的情況下進行。 |

對於明確的獨立易讀性審查、依賴概念的實質章節，或重複出現的理解失敗，請使用 [independent-reader-review.md](independent-reader-review.md) 中限定處理範圍的協定。獨立讀者應在沒有作者解釋的情況下檢查相同的完整單元；當無法取得個別讀者時，自我檢核仍應如實標註為自我檢核。純文法編輯仍應使用上述的局部通讀，而非自動進行多代理人稽核。

當「結果」（Results）行文讀起來像零散的筆記時，請在該通讀中使用 [result–explanation continuity check](results-and-explanation.md#resultexplanation-continuity)。定位已修復的關係或有正當理由維持原狀的發現；句子長度與添加的連接詞並非驗收標準。

請分開不同的報告基礎：掃描報告的是已設定的模式匹配；父層通讀報告的是已定位的讀者理解阻礙或有正當理由維持原狀的發現；獨立讀者報告則指出該讀者的實際處理範圍與限制。例如，工作流程發現可以指出某個段落現在提供了下一段所需的更新輸入。組件清單或籠統的 "flow checked" 並非那種證據。請將局部發現保留在行內，切勿印出每一對句子的觀察或建立另一本紀錄冊。即使掃描合格，尚未解決的理解問題發現仍應維持未結案狀態。

僅在具備具體的定位標記、發現內容以及已解決／未結案結果時，方可使用 `checked`。即使檢核已執行，未結案的發現仍屬未完成。請明確區分 `not_run`、`unavailable`（附註理由）以及 `not_applicable`（因該檢核超出已宣告的處理範圍／影響之外）。絕不可將無法取得的來源、作者豁免或無違規的禁用詞掃描結果轉化為合格通過。缺乏相鄰文字會限制連貫性驗證，但並不妨礙撰寫清楚標註的暫行局部草稿。

對於取決於前後脈絡的爭議或迴歸測試練習，請使用相符的 [evidence-context cases](evidence-context-cases.md)。它們能將規則缺失與執行或驗收落差區分開來。在測試修復方案時，請保留原始主張與來源事實；若句子改得較流暢卻遺漏了比較、改變了測量的構念或強化了推論，則該修復不可接受。

對於多層次的發現，通讀時還需定位各個連貫的證據單元在哪裡獲得其意義，以及下一個單元增添了什麼。請檢查量值或分析層級的改變，而非僅檢查段落邊界。最終的綜整無法彌補先前缺乏支持的排序或遺漏的比較。請記錄實際的阻礙或有正當理由維持原狀的發現；連接詞、SQ 標籤、定義或較短句子的存在，皆不能作為驗收證據。在此狹窄的練習中，請使用證據與脈絡案例 10 中的實際對照組；切勿因局部編輯而建立第二套檢核清單或稽核無關的章節。

對於多層次的比較，請在同一次通讀中增添一筆實質的轉述：此層次回答了問題的哪一部分、證據在該層次確立了什麼，以及下一項比較增添了什麼或必須交代什麼。定位能讓讀者在不具備專案歷史或 SQ／"first level" 標籤的情況下重構這些關係的措辭。若缺乏這種實質貢獻，流暢的句對與正確的數字依然不足。當沒有後續比較在處理範圍內時，切勿捏造橋接句，亦勿將診斷檢驗視為未說明的許可關卡。失敗與維持原狀對照組請參見證據與脈絡案例 11。自我檢核不等同於獨立讀者結果；交付時請保留此項區隔。

對於摘要性質的行文，同一次通讀也需檢驗讀者是否能重構出研究目標與對應的工作，而非僅看到方法或比較的清單。將轉述與編輯後確切的候選文本及當前來源綁定；檢查文字刪減或處理範圍修正是否擠壓了目標，或是將整體分析與次群體分析混為一談。定位保留的清晰措辭與修復的邏輯關係，或記錄有正當理由維持原狀的結果。請參見證據與脈絡案例 12。掃描結果、歸檔計畫或 SQ 標籤皆不能證明完成的段落已傳達了那些關係。

<a id="optional-deterministic-coverage-checker"></a>
## 選擇性確定性涵蓋檢核器

對於重複或多檔案的交付，請使用 `scripts/audit_handoff.py RECORD --json` 來驗證**涵蓋記錄**，而非驗證其發現的品質或真實性。它不需要受管的稿件狀態。若等效請重複使用現有記錄；切勿為了符合此格式而捏造第二套記帳系統。

此 JSON 約定支援舊版版本 `1` 與感知階段的版本 `2`：

- `schema_version`：整數 `1` 或 `2`；`scope`：`sentence`、`paragraph`、`section` 或 `package`；`change`：`surface` 或 `substantive`。
- 版本 `2` 亦需要 `action`：`plan`、`draft`、`revise`、`proofread` 或 `review`；以及 `checkpoint`：`outline`、`handoff`、`chapter_closure` 或 `full_review`。請依據實際的請求／工作來選擇，而非選擇檢核項目較少的設定檔。`proofread` 僅限表面。`chapter_closure` 使用實質的 `section` 處理範圍；`full_review` 使用 `package` 處理範圍。這兩個檢核點使用 `draft`、`revise` 或 `review`，而非規劃或校對。`outline` 檢核點用於規劃／推展／審查大綱，而非規避行文審查的手段；純文法的大綱修改使用 `handoff`。
- `features`：四個明確的布林值：`displays`、`formatted_file`、`venue_formatting`、`metadata_changes`。請誠實宣告影響；檢核器無法從文件內容推斷影響。即使未刻意變更中繼資料，格式化編輯仍需驗證身分。
- `artifacts`：非空的 `{id, path, role, sha256}` 記錄清單。路徑為絕對路徑或相對於涵蓋檔案的路徑；雜湊值涵蓋精確的檔案位元組。至少有一個角色為 `candidate`；其他角色為 `context`、`evidence` 或 `render`。請納入檢核中使用的目前相鄰文字／約定以及受影響的來源或渲染證據，以便在依賴項變更時使涵蓋度失效。
- `checks`：來自表格與下方版本 2 階段檢核的適用名稱，以蛇形命名法（snake case）表示。每個 `checked` 項目皆具備 `outcome`（`resolved` 或 `open`）、非空的 `artifact_ids`、`locator` 與 `finding`。待處理項目具備狀態與 `reason`。
- 已檢核的 `final_layout` 參照角色為 `render` 的產物，並在審查發現中與已儲存的精確候選對象及渲染程序綁定。已檢核的 `editor_identity` 亦記錄 `expected_author` 與 `new_edit_authors`；這些涉及本次編輯，而非所有歷史作者。清單若為空，則需要 `absence_reason` 記錄經檢查後確實無新增修訂／意見／回覆作者以及適用的身分檔案屬性；切勿純粹為了通過關卡而填入虛構作者。
- 已檢核的 `venue_basis` 亦記錄 `basis`（`verified_requirement`、`project_preference` 或 `example`）與 `source`（載明日期之官方來源或明確指示／範例定位標記）。來源字串不由本工具獨立查證。

對於無檔案／圖表展示／發表場域影響且保留原意的句子修改，僅需要 `meaning_and_evidence`、`language_scan` 與 `reader_walkthrough`。對於實質工作，亦需要 `progression_and_framing`。額外適用的檢核依據上述影響而定；必要的檢核不得標記為不適用。

版本 `2` 新增了以下涵蓋要求：

- 針對每項任務執行 `functional_completeness`，其處理範圍限於所要求的內容。
- 針對 `plan`、`draft` 或實質 `revise` 執行 `writing_plan`；參照目前大綱／約定，或記錄其功能、主張、證據、推展與橋接句。純審查工作不需要新的起草前主張。
- 針對 `full_review`、全套 `review`，或實質章節／投稿文件的起草、修訂或審查，執行 `argument_structure`、`evidence_scope`、`scholarly_writing` 與 `delivery_integrity`。大綱檢核點與純規劃工作不會觸發這些針對完成行文的檢驗輪次。
- 在章節結尾時執行 `chapter_closure` 與 `terminology_reconciliation`；全文審查亦需要 `terminology_reconciliation`。未解決的意涵請分開回報。經查證認定術語或決定均未變更的發現是可接受的；切勿為了迎合檢核清單而虛構詞彙表更新。

對這些檢核請使用相同的定位標記／發現／結果約定。若無法取得來源，請將受影響的必要檢核記錄為無法取得或未結案；切勿以記錄的存在將未解決的科學主張冒充為已解決。計畫項目可指向先前的大綱；不必將其全文複製。

當檢查依賴實際的共享狀態、相鄰文本、來源與相關規則檔案時，請將它們作為雜湊化的情境／證據產物一併納入。產物一旦變更，該紀錄即告失效。檢查結果會針對明確宣告的相依項目列出 `stale_artifact_ids` 與 `invalidated_checks`，因此在重新整理雜湊值之前，應保留未受影響的證據，並重新檢查受影響的項目。此清單並非語意影響偵測器：若有遺漏或新發現的相依項目，仍需進行判斷並擴大影響範圍檢查。

舊版紀錄會保留其原本的處理範圍／效果行為並回報 `coverage_basis: legacy_v1`，且不具備工作流程覆蓋率。若未明確升級至版本 `2`，便無法宣告新的工作流程欄位或階段檢查。版本 2 的結果會回報 `coverage_basis: workflow_v2`；這代表已宣告的階段覆蓋範圍，而非執行證明。切勿重寫舊憑證，假裝新檢查已經執行過。對於局部編輯，行內發現事項仍屬可接受；JSON 檢查器為選用性質，不會強制要求設置受管專案。

該 CLI 為唯讀且使用標準函式庫。針對 `COVERAGE_COMPLETE` 會回傳 `0`，針對 `INCOMPLETE` 回傳 `1`，若紀錄無效或發生讀取錯誤則回傳 `2`。每個結果皆明確聲明編輯品質**未經認證**。它無法單憑驗證雜湊值來偵測偽造的筆記、不實的適用性宣告、語意錯誤，或從錯誤文件產生的渲染輸出。`execution_order_certified` 恆為 false：結構化紀錄並無法證明時間先後順序、誠實閱讀、理解程度或科學正確性。

<a id="close-the-handoff-honestly"></a>
## 誠實完成交接

請回報已檢查的候選版本、已完成的適用覆蓋範圍，以及具體的剩餘限制。在來源或版面檢查尚待完成期間，臨時草稿仍可發揮作用；請勿將其標示為定稿、完全檢查完成或符合期刊規定。完整的紀錄在現有檢驗閘門下仍需要編輯與科學判斷。任何相關的文字用字、引用文獻、中繼資料、格式或相依項目的變更，都會使早先的驗收失效：交付前請更新確切的候選版本並重新檢查受影響的檢驗閘門。切勿因為這「只是初稿」而推遲這些檢查，也不要將無關的全套套件檢查強加於有界限的工作上。
