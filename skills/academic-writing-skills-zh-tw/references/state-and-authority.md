<a id="authority-hierarchy"></a>
## 權威層級

請建立專案專屬的層級架構，切勿假定有一套通用的來源順序適用於所有研究。實用的預設層級如下：

1. 經核實的原始證據：原始或處理後的資料、分析產出物、方程式、表格、圖表、逐字稿、來源語料庫或正式核准的中繼資料
2. 與該證據相扣合的當前研究方法與研究結果
3. 當前的討論與研究限制
4. 當前的摘要總結：摘要（Abstract）、重點精華（highlights）、結論、研討會摘要、投稿說明信（cover letter）
5. 僅作為參考之用的歷史草稿或相關稿件

當作者指明不同的權威來源時，請推翻此順序，並將此例外記錄下來。

切勿從字體排印、檔名、作者順序、星號、先前的論文或過時的摘要中推論事實。在有來源解決該問題之前，請將其標記為未知。

<a id="managed-project-records"></a>
## 受管專案記錄

請維護一份 `manuscript_state.json` 或同等的專案記錄，內容包含：

- 專案識別、稿件原型、生命週期階段與審查成熟度
- 作用中的產出物與歷史參考資料
- 權威來源及其處理範圍
- 稿件約定：研究缺口、任務、問題或目標、成果、貢獻與非主張事項（nonclaims）
- 語意鎖定與術語規則
- 語言變體、受保護的專業術語、允許的重複字詞以及專案不建議詞組
- 附帶來源的事實與中繼資料
- 缺口–問題–方法–證據–主張對齊項目
- 設計維度與報告欄位覆蓋率
- 決定與未解決問題
- 發布候選版本與必要檢核

以 `assets/manuscript_state_template.json` 作為起點。請將狀態保存在稿件專案旁，而非置於本技能內部。

此記錄提供的是背景脈絡，而非審查處理範圍。進行局部工作時，僅須查閱相關的來源、鎖定、術語及決策項目；重複使用輸入未變更的當前證據。切勿僅因任務只是進行中專案的另一個段落，就重新初始化新記錄、重啟每個發布檢核關卡，或重新開始全篇論文的審查。

請將風格設定檔視為專案指引，而非證明每個已登記詞組皆屬錯誤的憑據。即使確定性內文審查報告顯示使用頻繁，仍應保留專業術語與作者核准的措辭。

當專案或投稿管道要求既定的開放式複合詞（open compounds）即使在另一個名詞之前也必須保持分開書寫時，請將其登記在 `style_profile.preferred_open_compounds` 中。內文審查隨後會報告已登記的連字號變體，以供脈絡審查。

一致使用機器可審查的登錄欄位：

- 語意鎖定：`id`、`kind`（`EXACT` 或 `SEMANTIC`）、`canonical`、選填的 `required_roles` 以及選填的 `forbidden_variants`
- 術語項目：`id` 或 `concept`、`preferred`、選填的 `prohibited`（審查亦接受舊版 `avoid`）以及選填的 `scope_roles`
- 事實項目：`id`、`value`、`source_id`、選填的 `expected_strings`、選填的 `forbidden_strings` 以及選填的 `scope_roles`

切勿將諸如 `term/rule` 的純文字提醒存放在 `semantic_locks` 中，隨後聲稱通過了鎖定審查。請將其轉換為上述綱要結構，或記錄為需要手動核實的決策。無法被審查的登錄項目必須據實報告，切勿默默略過。

<a id="persistent-terminology-procedure"></a>
### 持久化術語程序

請維護反覆出現的構念、具重大影響的指標、縮寫及容易混淆的標籤，而非每個普通詞彙。請將這份單一共用記錄保存在論文旁。其既有的 `project`、`artifacts`、`contract`、`facts`、`alignment`、`decisions` 與 `issues` 能提供權威性與延續性；大綱或檢核記錄可直接參照這些內容，無須複製出第二份清冊。

持續寫作時，請使用既有的專案記錄或同等詞彙表作為共用字彙集，切勿依賴對話記憶。將其與當前稿件的身分識別及權威版本綁定。複製的記錄或吻合的主題，並不能構成對另一篇論文的權威。對於一次性的修改，作者提供的相關術語可直接保留在內文中；無須強制要求建立新的專案檔案。

1. 在動筆前，請閱讀相關的已確認概念、定義、偏好術語、明確允許的變體／縮寫以及處理範圍。辨識出必須保持區隔的概念。在需要處記錄定義／來源與確認出處；切勿從不熟悉的標籤憑空捏造定義。
2. 在寫作期間，請保留已定義概念的名稱，切勿輪替使用同義詞。作者明確的術語決策或指定的權威定義方可確認某個項目；助理在草稿中的用法則不行。請將新建議與未解決的意涵分開保存（例如存放在 `terminology_proposals`），並註明其來源與理由。若某個項目被明確標記為 `PROPOSED`，在任務重啟時切勿將其視為已確認。既有未註明狀態的舊項目將維持其既定的掃描行為，而非捏造核准出處。
3. 當出現新詞組時，判定其為經核准的變體、獨立概念，或可能是命名不一致。僅在未解決的意涵會影響所請求的主張時，才提出幅度最小的修復或進行詢問。切勿查禁所有新詞組，亦不可將意願、觀察到的行為、福祉及其他獨立構念混為一談。在實際語境中保護引文、文獻標題、官方調查工具名稱及有效屈折變化；切勿僅因某個詞在某處受保護，就將該詞設為全局豁免。
4. 在指定的章節邊界處，核對新確認的選擇與待處理的提議。對於作者核准的更名，在變更之前請先指明受影響的內文、圖表展示與附屬檔案。彼此衝突的已確認決策將維持未解決狀態，直到權威解決為止；僅憑時間較新並不代表獲得核准。
5. 對照當前記錄檢查確切的交付成果。在支援時，於審查證據中保留候選檔案與狀態的雜湊值、規則版本／雜湊值以及已檢查的處理範圍。變更登錄項目、規則、處理範圍或候選檔案，皆會使相關的先前證據失效，即使段落本身未曾改變亦然。

僅在任務需要術語協調時，空的登錄清冊才需要對現有權威資料進行有邊界的提議掃描；這不會阻礙文法修復。請將已確認的適用項目、未解決的概念與字面掃描結果分開報告。`PASS` 意指沒有符合設定的掃描結果，並不代表詞彙覆蓋完全或語意正確。若產出物角色不明，請揭示該項限制；切勿宣稱已獲得特定角色的檢核許可。當 `--label` 與提供狀態中的有效產出物 ID 完全相符時，本機 CLI 即可解析出角色。引號內的相符項仍屬脈絡診斷性質；指令碼並無法判定先前未登記的兩種表達方式是否指稱同一個概念。

對於已確認的項目，當需要區分意涵時，除了既有的可審查欄位外，請同時保留 `definition`、`allowed_variants` 與 `confirmation_source`。例如，作者的決定可能會確認以 `intention to enroll` 表示自陳的可能性，而保留 `enrollment` 用於觀察到的登記情形。這兩者並非同義詞。建議的替代詞應置於 `terminology_proposals` 中，並附帶其問題／來源與 `status: PROPOSED`，直到權威解決為止。這些描述性欄位有助於人工／代理的判斷；字面掃描並無法驗證定義或確認來源。

在工作重啟時，請比對論文識別身分與當前有效版本，接著僅讀取相關項目與未決決策。在章節交界處，請在同一份記錄中核對新確認的決定與仍待處理的提議。定義的變更可能會使比較失效，即使其句子本身未改變亦然；在重複使用舊證據之前，請先指明受影響的研究方法、圖表展示、摘要與檢核。切勿重啟無關的檢核。請使用 [execution-and-acceptance.md](execution-and-acceptance.md) 中的階段程序來記錄該邊界。

<a id="lock-and-change-rules"></a>
## 鎖定與變更規則

僅在使用者已明確定案或必須逐字保留的內容（例如正式的研究問題）時，才使用精確鎖定。當措辭可有所變化、但科學任務與處理範圍必須維持穩定時，請使用語意鎖定。

在變更鎖定之前：

1. 解釋提議的語意變更
2. 指明受影響的章節與產出物
3. 自使用者或指定來源取得授權權威
4. 記錄新決定已取代舊決定
5. 執行適用的影響檢核關卡

切勿純粹為了排比句結構、文體多樣性或縮減字數，就變更已被鎖定的意涵。

<a id="issue-and-version-states"></a>
## 問題與版本狀態

將問題狀態記錄為 `OPEN`、`RESOLVED` 或 `WAIVED`。豁免必須包含核准權威、原因、受影響的主張以及殘留風險。

將嚴重程度獨立於處理範圍之外使用：

- `S0`：僅限格式
- `S1`：局部可讀性
- `S2`：看似合理的誤解或局部不一致
- `S3`：主要論點、可重現性、跨檔案或投稿完整性風險
- `S4`：研究問題、證據有效性、主要結論、倫理或正式中繼資料風險

將證據狀態記錄為 `CONFIRMED`、`PROBABLE` 或 `UNVERIFIED`。

維護一份作用中的發布候選版本。將所有其他草稿標記為歷史記錄、已被取代或僅供參考。切勿使用如 `FINAL` 之類的檔名作為已準備就緒的憑據。

<a id="minimum-operating-procedure"></a>
## 最低操作程序

1. 找出作用中的檔案與相關來源。
2. 重複使用相關的專案狀態項目；僅在需要持續協調時才初始化或更新記錄。
3. 在相關時執行 `audit_manuscript_state.py` 進行狀態驗證或整合／發布工作，而非將其作為每次局部修改時強制執行的全新完整狀態審查。
4. 解決來源衝突，或將其保留為明確記錄的問題。
5. 執行所要求的審查或修改。
6. 更新受影響的狀態項目並執行影響檢核。
7. 執行功能完整性回顧。
8. 唯有在通過發布檢核關卡時，方可認證已準備就緒。

將檢核覆蓋範圍與問題／證據狀態分開報告：已檢查、不適用、超出請求的處理範圍，或來源無法取得／未核實。被排除的產出物既不算通過，亦不會自動成為完成較窄範圍任務的阻礙；但這確實會限制任何更廣泛的就緒宣稱。
